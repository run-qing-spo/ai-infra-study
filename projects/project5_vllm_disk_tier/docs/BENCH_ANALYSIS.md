# io_uring KV disk tier:实测结论

这份文档只记当前有效的结论和数据。调试过程中的错误归因和方法论教训
在 `BENCH_LESSONS.md`。

四个引擎参与对比。`uring` 是本项目的引擎,单线程 io_uring 批量提交,
单个大文件加 O_DIRECT(绕过页缓存的直接 IO)。`pool` 复刻 vLLM 官方
fs tier 的语义,Python 线程池,每个 block 一个文件。`pool-slab` 是消
融组,Python 线程池但改成单个大文件,用来把"线程池 vs 批量提交"和
"文件布局"两个变量拆开。`cpp-pool` 是 C++ 线程池,32 个 `std::thread`
各自做同步 `pread`/`pwrite`,文件布局和 uring 完全相同。

数据来自三台机器。

**dm 机**是自有实体机,没有 GPU。内核 5.15.0-119,单块消费级 NVMe
238G,ext4 建在 LVM 上(设备映射类型是 dm-linear)。盘的物理上限用
dd 直接读写测出来:写 2.2 GB/s,读 2.9 到 3.0 GB/s。

**md-RAID1 机**是 AutoDL 的 RTX 4090 实例。内核 5.15.0-97,XFS 建在
md0 上,md0 由两块 7TB 企业级 NVMe 组成 RAID1。端到端实验都在这台跑。

**md-RAID0 机**是另一台 AutoDL RTX 4090。内核 5.15.0-94,XFS 建在
md127 上,md127 由两块小 NVMe 组成 RAID0。这台的定量数据全部作废,
原因见 `BENCH_LESSONS.md` 的 bench 自伤一节。只有 punt 的定性结论
仍然有效。

## 1. 引擎在三台机器上的表现

### dm 机:io_uring 兑现全部承诺

QD(queue depth,队列深度)64,1024 个 1MB block,文件预写过:

| engine | store MB/s | load MB/s | cpu_util(store/load) | syscalls |
|--------|-----------|-----------|----------------------|----------|
| uring 单 ring | 2288 | 3000 | 0.14 / 0.21 | 28 / 26 |
| pool | 2229 | 3015 | 0.40 / 0.35 | 2048 |
| pool-slab | 1850 | 2684 | 0.42 / 0.49 | 1024 |
| uring shard4 | 2288 | 3016 | 0.16 / 0.21 | 28 |

`cpu_util` 的单位是核,算法是进程 CPU 时间除以墙钟时间。

三个引擎的吞吐都顶在盘的物理上限上,分不出高下。store 的 2288 MB/s
对应 dd 测出的 2.2 GB/s 写上限,load 的 3000 MB/s 对应读上限。有区分
度的是另外两条轴:uring 的 CPU 是线程池的两到两倍半,syscall 是线程
池的 1/75。单线程用 0.2 个核喂满一块 NVMe,这是 io_uring 应有的形状。

`uring shard4` 是分片对照组,四个引擎各开一个 ring。它和单 ring 完全
重合,说明单个 ring 已经打满盘,加并发没有余量可榨。

### md-RAID1 机:punt 仍在发生,但三条轴都赢

QD 32,1024 个 1MB block:

| engine | store MB/s | load MB/s | cpu_util(store/load) | syscalls | iou_wrk |
|--------|-----------|-----------|----------------------|----------|---------|
| uring | 3617 | 7270 | 0.38 / 0.65 | 63 | 5 / 6 |
| cpp-pool | 3422 | 7545 | 0.63 / 1.01 | 1024 | 0 |
| pool | 3534 | 6988 | 1.29 / 1.45 | 2048 | - |
| pool-slab | 3589 | 6973 | 0.93 / 1.26 | 1024 | - |

`iou_wrk` 是 io-wq 内核工作线程的峰值数量,非零说明请求被 punt(转
交给内核线程池)了。这台机器全程非零,punt 确实在发生。但是 uring
的 store 全场最快,load 和 cpp-pool 基本持平,CPU 只有线程池组的一
半到六成,syscall 是 1/16。

端到端实验前又复测了一轮,block 数加到 2048。形状完全一致:uring
store 3819 MB/s、CPU 0.41 核、syscall 127,cpp-pool 3799 / 0.66 /
2048,pool 3676 / 1.34 / 4096,pool-slab 3777 / 0.91 / 2048。load 侧
uring 7401 MB/s / 0.60 核,cpp-pool 7341 / 1.03。

### md-RAID0 机:只有定性结论

这台机器上 punt 同样发生,而且 write 被串成单列。iostat 看到的设备
排队深度(aqu-sz)只有 0.49,而 pool-slab 用 32 个线程能打到 15.5,
两者相差 30 倍。这条证据独立于 CPU 和吞吐的记账方式,所以定性结论
有效。

定量数据不能用。当时的 bench 有两处缺陷,把差距倍数放大了。

## 2. 优势来自提交模型,不是 C++

uring 引擎是 C++ 写的,pool 和 pool-slab 是 Python 写的。所以 uring
赢的 CPU 轴里可能混着"绕过 Python 全局解释器锁(GIL)"的语言加成。
为了拆开这个变量,补了 cpp-pool 对照引擎。它和 uring 共用同一套任务
描述结构、同样的单大文件加 O_DIRECT、bench 侧走同一条提交和轮询的
代码路径,唯一的差别是 worker 侧换成 32 个 `std::thread` 做同步读写。

dm 机,QD 64,32 线程,1024 个 1MB block,预写过,跑两轮取区间:

| engine | store MB/s | load MB/s | cpu_util store/load | syscalls |
|--------|-----------|-----------|---------------------|----------|
| uring 单 ring | 2285–2288 | 3004–3005 | 0.11–0.13 / 0.21 | 27–29 |
| cpp-pool | 2284–2289 | 2893–2929 | 0.26–0.44 / 0.46–0.67 | 1024 |
| pool | 2224–2238 | 2984–3025 | 0.37–0.40 / 0.36–0.39 | 2048 |
| pool-slab | 1703–1899 | 2673–2677 | 0.43 / 0.38–0.57 | 1024 |

**GIL 税约等于零。** cpp-pool 和两个 Python 池挤在同一档,都是 0.3
到 0.5 个核。把线程池从 Python 换成 C++ 根本不省 CPU。原因是 1MB
块的负载下,每个任务就是一次立刻释放 GIL 的大 syscall。解释器那边的
工作量只有一次函数调用加一个内存视图切片,相对每个 IO 几百微秒的内
核路径可以忽略。线程池的 CPU 大头在内核侧,是每个 IO 的提交、睡眠、
唤醒和上下文切换,换语言这些一分都不少。

因此 uring 的两到三倍 CPU 优势和 37 倍 syscall 优势可以干净地归给提
交模型。uring 用 0.11 到 0.21 个核,cpp-pool 用 0.26 到 0.67 个核,
两者同为 C++、同样的文件布局、同样走 O_DIRECT,唯一的变量就是"单线
程批量提交"对"每线程一次同步 syscall"。

线程池之间分不出稳定高下,不要过度解读。pool-slab 的 load CPU 两轮
分别是 0.57 和 0.38,单轮数字的噪声就有 50%。

盘瓶颈下 MB/s 没有区分度,CPU 和 syscall 才是有信息量的轴。这正好是
vLLM 场景想要的形状:同样喂满盘,谁给 attention 和 decode 留的 CPU 多。

## 3. punt 机制:io_uring 什么时候退化成线程池

io_uring 对每个 IO 先带 NOWAIT 标志尝试内联下发。下面任何一层返回
-EAGAIN,请求就被 punt 给 io-wq 内核线程池,走同步阻塞路径。io-wq
有一条规则:普通文件的 write 按 inode 做 hash,同一个 inode 的 write
全部串到同一个 worker 上顺序执行。这是内核为了防止缓冲写在 `i_rwsem`
锁上互踩的设计。read 不做 hash,可以摊到多个 worker 并行。

触发条件在块设备层。md(多设备,即软件 RAID)对 REQ_NOWAIT 的支持
5.17 才进主线。5.15 内核加 md 设备,带 NOWAIT 的 bio 打到 md 上直接
被弹回 -EAGAIN,内联提交必然失败,变成 100% punt。

证据链有三环。第一环是观测:io-wq worker 是本进程的线程,在
`/proc/self/task/*/comm` 里名字叫 `iou-wrk-*`,内联提交成功时这个数
只能是 0,非零就是 punt 的直接目击。第二环是干预:让四个 ring 并发
写同一个文件,吞吐照样翻倍,说明串行不在文件系统或 inode 层,只在
单个 io-wq 内部的 hash 链上。第三环是版本对照:dm 机和 md 机同为
5.15 内核,唯一的变量是 dm 还是 md,而 dm-linear 从 5.9 起就支持
REQ_NOWAIT 直通。dm 机上 load 的 iou_wrk 归零,punt 消失。

punt 还有第二个来源,在文件系统层。引擎用 `posix_fallocate` 预分配
backing 文件,分配出来的是 unwritten extent,也就是已分配但从没写过
的区间。首次写要把它转成 written,这一步带 NOWAIT 做不了,同样返回
-EAGAIN。dm 机上实测,store 的 iou_wrk 是 6,把文件预写一遍之后降到
0。引擎因此有一个 `prewarm` 开关,启动时把 backing 文件真写一遍零,
把所有 unwritten extent 翻成 written。manager 那边默认打开,启动开销
约 9 秒。

两个 punt 源有先后顺序。md 宿主上块设备层先把 NOWAIT 拦死,文件系统
层的 extent 状态根本轮不到起作用。prewrite 探针可以验证这一点:同一
个文件连写两遍,第一遍全是首写、第二遍全是覆盖写,墙钟 0.283 秒对
0.278 秒,iou_wrk 峰值 7 对 5,punt 完全不随 extent 状态变化。所以
"初始化预写能消掉 punt"这条只在裸盘或者 dm 宿主上成立。

**punt 是机制,不是判决。** 同样是 100% punt,两台 md 机的结果完全
相反。RAID0 加小盘那台,write 串成单列卡住吞吐,io-wq 还吃掉数倍
CPU。RAID1 加企业盘那台,串行单列照样打满阵列,而且 5 到 6 个内核
worker 比 32 个用户线程还省 CPU。

原因是 punt 的伤害分两笔账。第一笔是 write 的 per-inode hash 串行,
伤害取决于盘的单 IO 延迟。企业盘有掉电保护写缓存,1MB 写只要 0.3
毫秒量级,串行单列也能打出 3.5 GB/s 以上,直接顶到阵列上限。第二笔
是 io-wq 的 CPU 税,5 到 6 个内核 worker 远比 32 个用户线程便宜。

所以部署判据不能是"看有没有 punt",要看 punt 之后的对照数字。发现
`iou_wrk` 非零时,先跑四引擎微基准,用数字下判决,不要直接换机器。

## 4. 端到端:vLLM 里的 TTFT 和 CPU 记账

在 md-RAID1 机上跑,vLLM 0.24.0 加 Qwen2.5-7B-Instruct bf16,
`--max-model-len 16384`。负载是 16 个会话,每个 6000 词前缀先 prime,
然后 24 个一次性请求做 churn 把前缀从 GPU 和 CPU 逐级挤出去,最后
16 个会话 revisit。CPU tier 故意只给 4 GiB:这个模型每个 token 的 KV
大约 56 KB(28 层乘 K 和 V 乘 4 个 kv-head 乘 128 维乘 bf16),一个
8k 前缀约 440 MB,16 个会话约 7 GB,必然溢出到盘。踩不到盘的配置量
出来全是安慰剂。四组由 `bench/run_e2e_overnight.sh` 一次跑完,全程
9 分钟,原始数据在 `results_e2e_20260711_0058/`。

TTFT 是 time to first token,首个 token 的延迟。

| 组 | 配置 | revisit mean | p50 | p99 | revisit/prime |
|----|------|-------------|-----|-----|---------------|
| A | 无 offload | 648.6ms | 648.4 | 654.9 | 0.98 |
| B | CPU tier 4 GiB | 649.7ms | 650.1 | 654.9 | 0.96 |
| C1 | CPU + 官方 fs tier | 139.3ms | 139.5 | 151.1 | 0.20 |
| C2 | CPU + uring tier | 123.3ms | 121.4 | 139.4 | 0.18 |

前一夜有一次独立复跑,C1 是 147.0ms、比值 0.21,C2 是 128.0ms、比值
0.19。两次运行的方向和幅度一致,不是噪声。

B 组约等于 A 组,这不是失败,是容量论证。4 GiB 装不下 7 GB 的工作集,
churn 再灌 11 GB 把残存的也冲光。多一层内存在容量不够时等于零,这正
是磁盘层的入场理由。

磁盘层的价值是 C1 那一行。它把 revisit 从全量 prefill 的 650ms 打到
139ms,快 4.7 倍。从盘上读 440 MB 回 CPU 再上 GPU,比重算 8k token
的 prefill 便宜得多。

uring 对官方 fs tier 的赢面是 mean 低 11%、p99 低 8%(151ms 降到
139ms),而且 C2 的 revisit 分布明显更窄。

### CPU 记账:fs tier 把 IO 记在引擎进程头上

负载全程用 pidstat 采样,5 秒粒度,同时每秒数一次 io-wq 线程:

| | EngineCore %CPU | 其中 %system | io-wq 线程 |
|--|-----------------|--------------|-----------|
| C1(fs) | 110–121% | 12–20% | 全程 0 |
| C2(uring) | 97–101% | 2–3.5% | 稳定 8 |

C1 的 fs tier 在引擎进程内用线程做同步文件 IO,系统调用和数据拷贝
全部记在 EngineCore 账上,比无盘基线(约 100%,忙循环)多付大约 15
个点,而且几乎全是内核态。C2 的 EngineCore 和无盘基线几乎没有差别,
提交线程只花 2 到 3 个点,搬运挪给了 8 个 io-wq 内核 worker。

这里要诚实:io-wq 是内核线程,pidstat 不记它们,单看这张表不能下
"总 CPU 更低"的结论。补充证据是同一块盘上的微基准,那里的 cpu_util
包含 worker 成本,punt 路径的总 CPU 仍然全场最低。两笔证据互补。
延迟敏感的调度线程不被内核态 IO 打扰,大概率也是 C2 的 p99 更紧的
原因。

盘还有大量余量。iostat 显示 revisit 阶段读峰值只有 270 MB/s,设备
利用率不到 10%。这场赢在路径效率,不在带宽。工作集和并发还有一个
数量级的加压空间,CPU 记账的差距会随之放大,因为 fs 的 15 个点是按
IO 量走的,uring 的 2 到 3 个点近乎常数。

## 5. fs tier 输在元数据面

官方 fs tier 每个 block 存一个文件。一万五千个 block 就是一万五千条
dentry(目录项缓存)和 inode。假说是这样:元数据缓存一失效,每次
load 的 `open()` 就要去盘上取。

端到端证不了这个假说,有三个原因。压舱进程同时压页缓存和 slab 缓存,
是混杂变量。TTFT 把 open 的成本埋在 prefill 里,看不见。而且没有任何
一组能单独关掉"文件布局"这一个自变量。

于是把它剥成纯 IO 微基准(`bench/meta_probe.cpp`),不要 GPU、不要
vLLM、不要模型。宿主是 ext4 建在 LVM 上,14 GiB 内存,15000 个块乘
0.875 MiB,对齐端到端里实测的 15574 个 kv_fs 文件,每档随机读 10000
次。原始数据在 `results_meta_20260714_0949/`。

布局分三组,读路径完全对齐,都是 O_DIRECT、同样的块大小、同样的随
机块序列。`files` 是 N 个小文件,散在三层 hash 子目录里,每次读打开
一个不同的文件。`slab` 是单个文件复用一个 fd。`slab-reopen` 是单个
文件但每次读都重新打开一遍。

第三组是刀刃。它和 `files` 的 open 次数完全相同,唯一的差别是 dentry
有 15000 条还是 1 条。冷条件下如果 `files` 涨而 `slab-reopen` 不涨,
贵的就不是 `open()` 这个 syscall 本身,而是那一万五千条 dentry。两者
一起涨,假说当场被证伪。

缓存条件分四档,靠 `drop_caches` 做因子分离。`hot` 是全热。`drop2`
只丢 dentry 和 inode 缓存,重建它们要读的目录块和 inode 块还在页缓存
里,所以有 CPU 重建成本但不读盘。`drop3` 是元数据缓存和页缓存全丢,
重建必须真的读盘。`ballast` 是持续内存压力,和端到端对齐。`drop2` 和
`drop3` 的差就是盘上元数据 IO,`drop2` 相对 `hot` 的涨幅就是纯 CPU
重建。这两笔账第一次分开量。

open 延迟的均值,单位是微秒:

| layout | hot | drop2 | drop3 | ballast |
|--------|-----|-------|-------|---------|
| files | 3.6 | 12.2 | 154.1 | 186.2 |
| slab-reopen | 3.2 | 3.5 | 3.6 | 4.0 |
| slab | 0(整个 probe 只 open 一次) | | | |

`files` 涨了 43 倍,`slab-reopen` 在同样的 open 次数下纹丝不动,只涨
了 0.4 微秒。假说成立,反面没有出现。分账的结果是纯 CPU 路径重建 8.7
微秒,盘上元数据 IO 141.9 微秒,IO 是 CPU 的 16 倍。缓存回收确实占
CPU,但那不是主要矛盾。

iostat 给出了机制的直接观测。同一块盘,同样的数据量,唯一的变量是
文件布局:

| 档 | 读 r/s | 平均请求尺寸 |
|----|--------|-------------|
| files_hot | 1311 | 772.9 KiB |
| files_drop3 | 9757 | 88.5 KiB |
| slab_drop3 | 1108 | 797.3 KiB |
| slab-reopen_drop3 | 1134 | 779.1 KiB |

每次 `open` 要多付大约 8 次设备读。算法是 9.2 秒乘 9757 r/s 得到
89764 次设备读,减掉 10000 次数据读,剩下 79764 次除以 10000 次 open,
等于 8.0。这个数对得上 ext4 的路径结构,三层目录加文件,每一级都要
读目录块和 inode 块。平均请求尺寸也验算得通:10000 次乘 896 KiB 加
79764 次乘 4 KiB,除以 89764 次,约等于 103 KiB,实测 88.5 KiB。

代价是 29% 的数据吞吐,从 1340 MiB/s 掉到 953 MiB/s。4 KiB 的小读吃
掉了设备的 IOPS 和队列深度预算,大块数据读只能排队。

这和端到端的观测闭合了。端到端里看到 fs 的设备请求尺寸是 135 到 250
KB,uring 是 342 到 500 KB,fs 的排队深度在 16 并发时掉到 4 到 6。当
时的归因是"每文件元数据路径既偷走设备队列深度又碎掉 IO 尺寸",那是
从现象反推的假说。微基准把它变成了直接观测,请求尺寸从 773 KiB 崩到
88.5 KiB,请求数是 7.4 倍。归因从假说升级为已验证。端到端没碎到
88.5 KiB,是因为那里元数据缓存部分命中,方向和量级都自洽。

有一个读数陷阱记录在案。所有 `ballast` 档的墙钟都涨到 24 到 25 秒,
吞吐掉到 343 到 368 MiB/s,`slab` 和 `slab-reopen` 也一样。这是内存
压力带来的系统级减速,页回收和分配路径都变慢,对三种布局是对称的,
不影响 open 延迟的横向对比。但那几个吞吐数字不能跨档比较。

## 6. 当前的引擎参数

**gather window。** worker 提交前先判断队列余量。如果余量小于阈值,
而且还有 IO 在飞、待发队列没抽干,就跳过这轮提交,让完成路径阻塞等
一批 CQE(完成队列条目)攒够余量再回来。没有这个窗口时,每完成 1 个
IO 就补 1 个 SQE(提交队列条目)立刻提交,退化成"用 io_uring 的 API
写同步 IO"。实测 batch 分布从"1024 次 batch=1"变成"32 次 batch=32",
syscall 少 30 倍。

**阈值随 QD 联动,取 `max(1, min(32, QD/2))`。** 阈值写死 32 时,如
果 QD 也是 32,会退化成"提交 32 个、等完 32 个"的 lockstep。联动之后
QD=32 时等 16 个补 16 个,任何时刻盘里至少有半数 IO 在飞。

另外有个死锁要避免。阻塞等待的数量必须用 `min(阈值, in_flight)` 封
顶。QD 小于阈值时 in_flight 永远到不了阈值,worker 会永久卡住。

**默认 QD 是 32。** 更大的 QD 在 md 机上会让 load 吞吐暴跌,原因是
io-wq 的 worker 伸缩在大批量入队时坍缩,QD=512 时全程只有 1 个 worker。
dm 机上 QD 从 32 到 256 吞吐完全平坦,瓶颈在提交线程,轮不到队形问题
出场。

**registered buffers 没做,优先级低。** 这个优化是注册时把内存 pin
一次,之后每个 IO 免掉 `get_user_pages_fast`。它治的是"每个 IO pin
页打满单核"这个病,而修掉 bench 缺陷后单核只用 0.2,没有吞吐病可治。
作为 CPU 微优化仍然有意义,已驻留页的 GUP 也有百纳秒级成本,对 vLLM
场景省 CPU 有价值,但排在端到端之后。

## 7. 面试版

**主线。** 我做了一个 io_uring 的 KV cache 磁盘层,替换 vLLM 官方的
fs tier。端到端结果是首 token 延迟的均值降 11%、p99 降 8%,同时把
同步 IO 的大约 15 个点 CPU 从推理调度进程里挪走。微基准侧,单线程一
个 ring 用 0.2 个核喂满一块 NVMe,CPU 是线程池的一半,syscall 是 1%。

**追问:优势是 io_uring 的还是 C++ 的?**
有人质疑我赢线程池是 C++ 对 Python 的语言差,我补了一个同构的 C++
线程池对照。结果是 C++ 化根本不省 CPU。1MB 块的负载下每个任务就是
一次立刻释放 GIL 的大 syscall,GIL 收不到税,线程池的 CPU 账单其实
在内核侧,是每个 IO 的提交和唤醒路径。io_uring 的两到三倍 CPU 优势
和 37 倍 syscall 优势因此干净归给提交模型。顺带学到一条:"去掉 GIL
必有收益"是个想当然的默认,做了对照才知道税基根本不在那里。

**追问:io_uring 什么时候不管用?**
它的收益前提是 NOWAIT 内联提交成功。5.17 之前的内核里 md 软件 RAID
不支持 REQ_NOWAIT,所有 IO 会 100% punt 到 io-wq 内核线程池,write
再被 per-inode hash 串成单列。我用三环证据钉死了这条链:iou-wrk 线
程计数直接目击 punt,同一个 inode 多个 ring 分片照样提速排除了文件
系统层,同为 5.15 内核的 dm 机上 punt 消失锁定了变量是 md 而不是内
核版本。

**追问:那 punt 就不能部署了?**
不对,这是我被复测教育的一点。我本来把 iou_wrk 非零当成"不可部署"
的判据,后来在另一台 md 机上,同样 100% punt,uring 的三条轴全赢。
punt 的伤害取决于盘的单 IO 延迟:企业盘 1MB 写 0.3 毫秒量级,串行
单列照样打满阵列,而 5 个内核 worker 比 32 个用户线程还省 CPU。所以
部署判据从"看有没有 punt"改成"看 punt 之后的对照数字"。警报和判决
是两件事。

**追问:官方 fs tier 具体输在哪?**
我没有停在"大概是元数据开销"。我把它做成了一个可证伪的微基准:同
一块盘、同样的数据量、O_DIRECT 读同样的块序列,唯一的变量是文件布局。
关键是我加了一组"单文件但每次重新打开",它和多文件组的 open 次数完
全相同,只差 dentry 是一条还是一万五千条。缓存被回收之后,多文件组
的 open 从 3.6 微秒涨到 154 微秒,单文件重开组纹丝不动。贵的不是
open 这个 syscall,是那一万五千条 dentry。iostat 把机制照了出来:每
次 open 要多付 8 次设备读,设备平均请求尺寸从 773 KiB 崩到 88.5 KiB,
数据吞吐掉 29%。这正好解释了端到端里 fs 的请求尺寸只有 uring 一半、
队列深度喂不满设备。

# 调试教训

project5 的 uring 引擎从"看起来全面负优化"调到"三条轴全赢",中间错
了五次归因,还发现两处 benchmark 自己伤自己。结论和数据在
`BENCH_ANALYSIS.md`,这里只记走过的弯路。

---

## 1. 五次错误归因

### 一、QD 越大越慢,以为是 NVMe 的物理队列深度

队列深度(QD)从 32 加到 512 之后,load 的吞吐反而暴跌。当时的解释
是 NVMe controller 的物理队列深度通常就是 32 到 128,超过就是内核端
排队,到不了设备端。

推翻它的是 iou-wrk 线程计数。QD=512 时全程只有 1 个 io-wq worker。
真正的原因是 io-wq 的 worker 伸缩逻辑在大批量入队时坍缩,并行度死在
内核线程池里,和 NVMe 的队列深度没关系。同一批数据里 pool-slab 用
32 个线程能打 7500 MB/s,设备远没有到顶,这本来就该让我怀疑设备侧
的解释。

现象是对的,QD=32 至今仍是默认值。错的是解释。

### 二、写被串成单列,以为是文件系统层

iostat 显示 uring 的设备排队深度只有 0.49,而 pool-slab 有 15.5,相
差 30 倍。当时怀疑两个对象:inode 的 `i_rwsem` 读写锁,或者 md RAID
层对单个 fd 的 O_DIRECT 写做了排队。

推翻它的是分片实验。让 4 个 ring 并发写同一个文件,吞吐照样翻倍,
和写 4 个不同文件的结果完全重合。同一个 inode 能被 4 个 ring 并发写,
说明文件系统和 md 层允许这个 inode 并发。串行只能发生在 uring 独有
的路径里,也就是单个 io-wq 内部的 per-inode hash 链。每个 ring 有自
己的 io-wq,互不共享 hash 链,所以分片能绕开。

其实 pool-slab 的数据当时就藏着反驳:它写的也是同一个大文件同一个
fd,32 个线程的 pwrite 能打出 15.5 的排队深度。串行不可能发生在两条
路径共用的层。这条反驳摆在眼前,我隔了一层诊断才用上。

### 三、单核喂不满盘,以为是稳态 pin 页的成本

perf 按线程号拆开之后,worker 线程有一条贯穿的热点调用链:
`io_uring_enter → io_submit_sqes → ext4_dio_write_iter → iomap_dio →
bio_iov_iter_get_pages → get_user_pages_fast → 缺页 → 页分配 → 清零`。
当时归因成每个 IO 要 pin 256 个页,这是内联提交路径的稳态成本,开的
处方是 registered buffers,注册时 pin 一次,之后每个 IO 免掉 GUP。

推翻它的是 pre-touch。把缓冲区分配后整块摸热,单个 ring 直接打满盘,
只用 0.14 到 0.21 个核。被串行的主体是首次触碰的缺页,那是 benchmark
的产物,不是稳态成本。每个页的缺页路径要进 fault handler、分配、清
零 4K、建页表,是微秒级;GUP 一个已经驻留的页只要百纳秒级。差两个
数量级。

这一条的教训最值钱:**perf 采样显示缺页只占 worker 的 25%,但干预
实验给出的真实份额是"从 1700 MB/s 到打满盘的全部差距"。** 采样比例
会骗人,成本会摊在 percent-limit 之下的长尾符号里。观测只配提出假设,
份额要靠干预来定。

### 四、线程池 CPU 高,以为是 GIL 争用

早期有一组数据是 pool-slab 的 load 打了 16.4 个核,uring 只用 4.2 个。
当时归因成 Python 全局解释器锁(GIL)争用加上线程上下文切换把线程池
玩崩了。

两件事推翻了它。第一,那个数字本身不可信:它是在下面第 2 节说的坏口
径下测的,带 iou_wrk 计数复测时 pool-slab 的 load 稳定打 7500 MB/s、
只用 1.3 个核。16.4 和 1.3 差 12 倍。第二,补了 cpp-pool 对照引擎之
后,C++ 线程池和两个 Python 池的 CPU 挤在同一档,GIL 税约等于零。

真正的原因是 1MB 块的负载下,每个任务就是一次立刻释放 GIL 的大
syscall。线程池的 CPU 大头在内核侧,是每个 IO 的提交、睡眠、唤醒和
上下文切换。换语言这些一分都不少。

"去掉 GIL 必有收益"是个想当然的默认。做了对照才知道税基根本不在
那里。

### 五、把 punt 当成"不可部署"的判据

io_uring 内联提交失败会把请求 punt 给 io-wq 内核线程池。在 RAID0 加
小盘那台机器上,punt 让写串成单列、CPU 涨了几倍,当时的结论是"CPU
卖点在这个环境不成立",而且把 `iou_wrk` 非零直接当成筛机器的红线。

推翻它的是另一台 md 机的复测。RAID1 加两块企业级 NVMe,同样 100%
punt,uring 的三条轴全赢:store 全场最快,CPU 只有线程池组的一半到
六成,syscall 是 1/16。

punt 的伤害分两笔账,都取决于硬件。写的 per-inode hash 串行,伤害
取决于盘的单 IO 延迟,企业盘有掉电保护写缓存,1MB 写只要 0.3 毫秒
量级,串行单列照样顶到阵列上限。io-wq 的 CPU 税,5 到 6 个内核
worker 远比 32 个用户线程便宜。

所以"md 加 5.15 内核就惨"这个推广是错的。两台机器的数据都对,错的
是推广。判据要改成"看 punt 之后的对照数字",不是"看有没有 punt"。
警报和判决是两件事。

## 2. 两处 benchmark 自伤

这两处缺陷让 RAID0 那台机器的全部定量数据作废,也是上面第三、第四
条错误归因的直接来源。

**主线程忙轮询污染 CPU 轴。** bench 的主线程轮询任务完成情况,空返
回时调用 `time.sleep(0)`。这个调用只让出 GIL,不让出 CPU,主线程因
此恒占 1 个核。测出来的 `cpu_util` 里混着这 1 个核,反映不了 worker
那边的真实成本。修法是空轮真睡 0.5 毫秒,对秒级的墙钟影响可以忽略。

**首次触碰缺页加引擎顺序污染吞吐轴。** `make_region` 分配缓冲区之后
只摸了每个 1MB block 的第 1 页,剩下 255 页留给内核在 GUP 时首次触碰。
更麻烦的是每个方向只建一次缓冲区,三个引擎共用,而 uring 排在引擎
列表的第一个。所以 **uring 替所有引擎付了全部缺页税,后面的 pool 拿
到的是已经摸热的缓冲区。** 修法是分配后整块 pre-touch,把缺页赶出计
时窗口。

教训是:对照组共享可变状态时,运行顺序本身就是混杂变量。

修掉这两处之后,"uring 全面负优化"完整拆成了三层:一层是环境,md
在 5.17 之前不透传 REQ_NOWAIT,100% punt 进 io-wq 被 per-inode hash
串行;两层是 benchmark 自伤。三层剥掉之后,io_uring 在它适用的环境
里兑现了全部承诺。

## 3. 冷条件会自我衰减

做元数据微基准时,用 `drop_caches` 清掉 dentry 和 inode 缓存来构造
冷条件。首版数据的均值被稀释了 85%,衰减曲线从每桶 287 微秒一路掉
到 11 微秒。

原因是元数据体积很小。15000 个 inode 才几 MB,一次性 drop 之后头
100 次读就把它们读回页缓存了,后面全是热态。而且 iostat 的 1 秒粒度
根本抓不到那 0.07 秒的冷窗口,想事后核对都没有数据。

解法是加 `--redrop-every 100`,每 100 次读重新清一遍,让全程都冷。
改完之后衰减归零,各档前后半的差在 ±1% 以内,均值才是稳态值。

这个改法也更贴近真实场景。端到端里 churn 阶段一直在写新文件,元数
据缓存本来就在被持续冲刷。

## 4. 压舱压不住元数据,归因要改

端到端的冷组用 ballast 进程占住内存,构造内存压力。一直以来把 fs
tier 在冷组的劣化记在 ballast 头上。

元数据微基准的首版数据反过来打了 ballast 一巴掌:`ballast` 档和
`drop3` 档的衰减曲线一模一样,一个是 301 降到 11,一个是 287 降到
11,两者都衰减 85%。也就是说 ballast 那 4 GiB 的余量根本压不住元数
据缓存的重建。15000 个 inode 才几 MB,4 GiB 装得绰绰有余。ballast
的目标值是按 12.8 GB 的数据工作集定的,它只压住了数据缓存,元数据
从来不在它的射程内。

所以冷组里 fs 的元数据面之所以是冷的,主因不是内存压力,而是 churn
阶段持续写入几万个新文件、不断冲刷元数据缓存。

这个修正没有削弱结论,反而扩大了适用面。E3 和 E4 两组根本没有压舱,
fs 照样系统性地输,那里的元数据缺失本来就来自"文件数太多加持续写入
冲刷"。元数据这条归因解释的是 E3 和 E4 的主战场,不只是 E1 的边角。

## 5. 文档结构本身会骗人

这份记录原来和 `BENCH_ANALYSIS.md` 是同一个文件,按调试的时间顺序
写:先写当时的诊断和结论,后来被推翻了就在下面挂一条【后记】。20
多条后记攒下来,文档变成 975 行,而且正文里写着已经作废的结论。

2026-07-20 拿到了一次实测。让 Claude 读这份文档,它搜到 §4 那段
"pool-slab 打了 16.4 核,说明 GIL 争用把线程池玩崩了"就开始往下推
理,完全没有看到 200 行之后的复测后记说那是异常样本,也没有看到
§11 说 GIL 税约等于零。它连着两轮给出错误的分析,直到被要求读完
整节才发现那个数字早就作废了。

人读也一样。面试时被追问到这一段,照着正文讲就会翻车。

所以结论作废就把正文删掉,不要用打补丁的方式纠正。有价值的弯路单
独成文,像这份文档,让"当前结论"和"走过的弯路"各自完整,谁也不
污染谁。

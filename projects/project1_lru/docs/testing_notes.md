# LRU 项目测试 —— 核心洞察

## 一、最重要的一条:锁保护的是**资源**,不是代码段

新手容易把锁理解为"包住一段代码,让一次只有一个线程能进入"。这是症状,不是本质。

**锁的本质是对某一组资源(对象、字段、数据结构)的访问串行化**。代码段只是访问这些资源的路径 —— 同一组资源往往有**多条**访问路径,每一条都得被同一把锁罩住;反过来,如果某段代码不动这组资源,把锁包住它毫无意义,只是放大临界区拖慢吞吐。

正确的提问顺序是:**先列资源 → 决定哪把锁保护哪组 → 最后才看代码段**。

### LRU 里被那一把 `mutex` 保护的资源集合

`lrucache_mutex` 那把全局锁,保护的是下列**一整个**资源组:

1. `std::vector<Node> pool` 本身的物理布局
2. 每个 `Node` 的 `next` / `prev` / `value` / `key` 四个字段
3. `std::unordered_map<K, int32_t> key2idx` 的内部结构(桶数组 + 链节点 + size)
4. 由 `pool[i].next/prev` 编织出的两条链表 —— used 和 free
5. `_head_free` 这个整数游标

**这五项必须当作一个原子整体看**:任何一项被别的线程看到"中间状态",整套都会乱。所以一把全局锁等于这样一句契约:

> 任意一次 `push`/`get`/`erase` 都把这组资源从一个**完整快照**带到另一个**完整快照**,中间状态对外不可见。

为什么不拆成多把锁?因为这些资源**互相用 idx 引用**:`key2idx[K]` 是 pool 的下标,`pool[i].next` 是 pool 的下标,`_head_free` 也是。一旦拆锁,跨锁更新就需要两阶段协议或者别的同步原语,复杂度上一个量级 —— 这正是 `lru_sharded` / `lru_lockfree` 要解决的问题。

## 二、测试 = 检查"这组资源的状态对不对"

资源集合一旦列清楚,测试就有方向了:**反复扰动它们,然后断言它们还处在合法状态**。"合法状态"分两种"不合法":

### 形态 A —— **单个**数据结构自身坏掉

- used + free 应该不相交且并起来覆盖 `[0, capacity)` 全集
  - 漏一个槽 = 永久泄漏一个 slot
  - 重一个槽 = 同一个 slot 在两条链上,迟早被双重释放
- used 链长度应该 ≤ capacity —— 超了说明 evict 路径漏了一次
- 链表前向遍历的节点集合应该等于反向遍历的节点集合 —— 不等说明 `prev`/`next` 在某次操作里写漏了一侧

### 形态 B —— 数据结构**之间**对不上

- 对每个 used 链上的 `pool[i]`:必须满足 `key2idx[pool[i].key] == i` —— 不满足 = map 指向了错节点
- 对每个 `key2idx` 里的 K:对应 idx 必须在 used 链上 —— 不满足 = 有"幽灵 key"
- `key2idx.size()` 必须等于 used 链长度 —— 不等 = "map 删了链没删"或反过来
- 若业务约定 `value == key`(测试里我们就用这个 trick):`*(pool[i].value) == pool[i].key` —— 不满足 = push 路径里 value 被串到了别的 key

**`audit()` 函数干的事,就是把上述所有"应该满足"逐条检查一遍并报告第一个被违反的项**。它不是一个炫技工具,而是"资源状态契约"的可执行版本。production 头里用 `#ifdef LRU_TEST_HOOKS` 条件编译进去,生产编译时整段消失,零运行时开销。

## 三、4 层测试方法论都从这条线长出来

| 层 | 在"资源-状态"视角下到底在测什么 |
|---|---|
| **Layer 1** 单线程功能 | 每次操作之后跑 `audit()`,确认资源状态合法 —— 算法本身把不变量维护住了吗? |
| **Layer 2** 异常安全 | 让操作**中途**抛异常,抛完跑 `audit()` —— 异常路径上资源是否回到合法状态?是丢了东西(basic)还是如未发生(strong)? |
| **Layer 3** 并发 | 多线程扰动这组资源 —— 锁有没有把它们真的保护住? |
| **Layer 4** 性能 | 测的是"保护代价":锁把本来 O(1) 的访问串行化掉了多少 |

### Layer 3 的关键提问 = "锁实际保护住那组资源了吗?"

并发测试的判定不是"程序跑通了",而是**三个维度同时成立**:

| 检查 | 对应的"锁保护"含义 |
|---|---|
| TSan 报无 race | 没有路径绕过锁去读写那组资源 |
| `audit() == ""` | 资源状态没被并发破坏成不合法(形态 A / B 都没出现) |
| 内容层断言(如 `*get(k) == k`) | Node 的 `value` 字段没被竞争撕裂 |

三者**缺一不可**,因为它们分别对应:
- 锁的**存在**(没有未受保护的访问路径)
- 资源**容器**的完整性(数据结构层不变量)
- 资源**内容**的完整性(字段值不被串改)

> 我今天的关键失误就在这里:Layer 3 最初只查了第三条(内容层 `*sp == k`),没查 audit。被用户点出来才意识到"竞争撕裂应该体现在数据结构互相对不上",于是给 `lru_mutex` 加了 `audit()` wrapper、在 storm 之后补上 audit 断言。这一步把"并发测试到底在测什么"才真正想清楚。

## 四、围绕"资源状态"的几个实操要点

### 4.1 Layer 1 怎么用 audit

- 每个 public 方法之后都跑一次:`AuditHoldsAcrossOperations` —— early bug 立即定位到具体操作。
- 长跑 churn 测试里按比例采样:`AuditHoldsThroughHeavyChurn` 每 100 次操作 audit 一次 —— 不至于跑完才知道挂在哪。
- 任何**新加** public 方法都必须新增一条 audit 调用 —— 防止以后引入操作绕过状态检查。

### 4.2 Layer 2 怎么注入异常

写一个**会按需抛的类型**(`Throwy`)做 K,在 copy / copy-assign 里挂 `tick()` 计数器,`countdown == 0` 时抛。一次性,抛完关闭。**默认构造不能抛**,否则容器初始化就先挂了。

异常测试的判定永远是:**抛出之后 audit 是否还过**。过了说明资源状态合法,接下来再细问是 strong 还是 basic —— LRU 当前满容量下抛出会丢 LRU 项(basic),钉一条 documenting test 把它显式写出来:测试名直接叫 `PushThrowOnKeyAssignAtCapacityEvictsButDoesNotInsert`,以后谁改了行为这条测试就报红。

### 4.3 Layer 3 死锁兜底

裸 `join()` 死锁时会让 CI 永久 hang。改成:

```cpp
auto fut = std::async(std::launch::async, [&] { /* stress + join */ });
ASSERT_EQ(fut.wait_for(std::chrono::seconds(30)),
          std::future_status::ready) << "可能死锁";
fut.get();  // 把线程内未捕获的异常重抛
```

### 4.4 Layer 4 真正在测的"代价"

| 维度 | 含义 |
|---|---|
| `lru_base` vs `lru_mutex` 单线程吞吐差 | 锁本身的纯开销 |
| 多线程 1/2/4/8 扩展曲线 | 资源被串行化的程度 |
| 延迟 p50 / p95 / p99 / p999 | 锁等待的尾部 |

实测结论是 **8 线程吞吐反而比 1 线程低 5 倍**。这不是 bug,是"一把全局锁保护一组耦合资源"必然的代价 —— 也是后续做 sharded / lockfree 的硬证据。

注意:`steady_clock::now()` 本身 20-40ns 开销,对 ~40ns 的操作会把仪表噪声拍在真实延迟上,数字只用于横向对比,**不要对生产对标**。

## 五、留作"使用手册"的若干琐碎

- **`-DLRU_TEST_HOOKS`** 在 Makefile 测试构建里开,bench 构建里关。让 audit 在生产编译中完全消失。
- **TSan** 跑 `make test-tsan`,随机性测试(如 `ConcurrentMix`)要重复 3 次再下结论。
- **`std::async + wait_for`** 死锁兜底见 §4.3。
- **`std::atomic<bool>` 当 stop 标志、`atomic<int>` 当 ready 计数器、acquire/release 当 barrier** —— 不是为了"装并发",是因为非 atomic 跨线程读写是 UB,编译器会把 `while(!stop)` 优化成 `while(true)`。
- **`Hash` 作为模板参数 + 默认值 `= std::hash<K>`** 比全特化 `std::hash<MyType>` 干净:不污染 `std` 名字空间。
- **项目级 skill** 在 `.claude/skills/<name>/SKILL.md`,session 启动时扫一次,中途新增不会热加载。改 `lru_base.hpp` / `lru_mutex.hpp` 必须走 `lru-verify`(`make test` + `make test-tsan` + `ConcurrentMix` ×3)。

## 六、给下一次的自己

写并发数据结构的测试时,**永远先做这一步**:

1. **列出被锁保护的资源集合**(像 §1 那样)。如果列不清楚,说明锁的设计本身没想透,先停下来想清楚。
2. **写出 `audit()`**,把这组资源的"合法状态"逐条断言,函数返回第一条被违反的项。
3. Layer 1 / Layer 2 / Layer 3 全部围绕"audit + 内容层断言"展开,工具只是手段。
4. Layer 4 测的是"保护这些资源付出了多少代价"。

只要这条线想通,具体用什么测试框架、什么 sanitizer、什么 percentile 算法,都是工程师的工具箱问题,不构成核心竞争力。**核心竞争力是知道在测什么,以及为什么。**

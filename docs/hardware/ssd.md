# SSD 的能力边界与压榨路径

这篇要回答的问题是：一块 NVMe SSD 对外能提供多少能力，这个能力被什么卡住，我还能从哪里再压榨出一点。

最核心的理解是：

> 每个 I/O 都需要占用若干有限资源一段时间；资源数量有限、单次服务时间非零，所以每秒最多只能完成有限数量的 I/O。

它和餐厅很像。每桌顾客相当于一个 I/O，厨师、灶台、服务员分别对应 NAND die、控制器、PCIe 和 CPU。每桌无论只点一口饭还是点很多菜，都有接单、调度、制作和结账的固定成本。最慢、最繁忙的环节决定全店吞吐量。

## 优化只有三条路

把上面那句话拆开，优化的抓手就只有三个方向，全文所有的旋钮都能归到其中之一：

1. **让资源变多**：更多 channel、更多 die、更多队列、更多 CPU 同时干活。
2. **让单次占用时间变短**：更短的 NAND 延迟、更少的 syscall、更浅的软件栈。
3. **消除无效工作**：写放大、GC 搬迁、read retry、多余的内存拷贝，这些都在消耗资源却不产生对外能力。

第三条最容易被忽略，但往往是收益最大的一条 —— 因为它不需要换硬件。

# 第一部分 · 一次 I/O 的一生

先把完整路径摆出来，后面每一节对应链路上的一站：

```text
文件系统把文件偏移映射成磁盘 LBA
  → block layer 构造并可能合并 bio/request
    → NVMe 驱动选择提交队列
      → 写入 NVMe SQ，敲 doorbell
        → SSD 控制器通过 PCIe DMA 取命令和数据
          → FTL 完成逻辑地址到 NAND 物理地址映射
            → NAND flash 执行读/编程
              → SSD 写入 CQE，触发 MSI-X
```

每一站都问同一组问题：这里的有限资源是什么，饱和时是什么现象，我能拧的旋钮有哪些。至于每一站内部的机制怎么运转 —— `iocb` 长什么样、PRP 怎么描述内存、phase bit 怎么判断新完成项 —— 那是另一篇的事，见[一次 AIO 请求的全链路](/hardware/aio-path)，下面各站会给出对应小节的跳转。

## 1. 应用与 syscall：CPU 时间 {#cpu-cost}

即使 SSD 还没满载，主机也可能先到上限。每个 I/O 都要执行构造请求、系统调用、走文件系统路径、DMA mapping、提交队列操作、完成回调、回收对象。

如果每个 I/O 消耗 2 μs CPU 时间，一个 CPU 核的理论上限约是：

```text
1 / 2 μs = 500K IOPS
```

SSD 可能支持 1M IOPS，但单提交线程只能驱动到 500K。

还有一种更隐蔽的损耗：**提交路径本身可能阻塞**。libaio 的 `io_submit()` 遇到缺页、文件系统元数据锁、extent 分配时会原地等，此时提交线程既没在干活也没在等 I/O（[细节](/hardware/aio-path#submit-blocking)）。这是 `io_uring` 存在的主要理由之一 —— 它把可能阻塞的操作交给内核工作线程。

**能拧的旋钮**：多线程提交把 CPU 从一个核摊到多个核；`io_uring` 批量提交（一次 `io_uring_enter` 带多条 SQE）摊薄 syscall 固定成本；注册文件和缓冲区（`IORING_REGISTER_FILES` / `_BUFFERS`）省掉每次 I/O 的引用计数和 DMA mapping；再进一步是 SQPOLL 或 SPDK 用户态驱动，把 syscall 彻底从热路径拿掉。

## 2. 文件系统：偏移 → LBA {#fs-cost}

这一步把文件内的偏移翻译成设备上的 LBA。代价来自元数据：extent 树查找、inode 锁、日志提交。

buffered I/O 还要额外经过 page cache —— 多一次内存拷贝，多一层页管理和回写调度。对已经能跑到百万 IOPS 的盘，这层的 CPU 开销往往比它省下的那点缓存命中更贵。

**能拧的旋钮**：`O_DIRECT` 绕开 page cache 和拷贝；预分配（`fallocate`）避免写路径上临时分配 extent；大文件顺序布局让一次请求对应连续 LBA，给下游的合并创造条件；极端情况直接裸设备，跳过整个文件系统。

## 3. block layer：合并与队列 {#blk-mq}

这一层把请求构造成 bio/request，相邻的会被合并，然后交给下游。历史上单队列加自旋锁是明确的瓶颈，现在的 blk-mq 是 per-CPU 软件队列映射到硬件队列。

即使没有传统大锁，共享队列的 head/tail、统计计数和引用计数也可能在 CPU 之间反复迁移 cache line，造成 cache coherence 流量、原子操作等待、NUMA 跨节点访问，扩展性低于线性。

**能拧的旋钮**：`none` 调度器（NVMe 上调度器带来的排序收益通常抵不过它的开销）；确认软件队列到硬件队列是一对一而不是多对一；让提交线程绑核，避免请求在 CPU 间漂移。

## 4. NVMe 队列与 doorbell {#nvme-doorbell}

驱动挑一条提交队列，写入 SQE，然后敲 doorbell 通知设备。队列对数量有限（由设备的 `Number of Queues` 特性决定），每条队列的深度也有限。

doorbell 是一次 MMIO 写，会变成一个跨 PCIe 发到控制器的 Memory Write TLP，比普通内存写贵得多（[细节](/hardware/aio-path#doorbell)）。QD=1 时每个 I/O 一次 doorbell；有多个请求在手时，可以连续写多条 SQE 只在最后敲一次。

**能拧的旋钮**：保证队列数 ≥ 提交 CPU 数，做到 per-CPU 无锁提交；批量提交合并 doorbell；深队列让设备内部有更多请求可调度（这条的收益曲线见第 9 节）。

## 5. PCIe：DMA 搬命令和数据 {#pcie-bw}

控制器通过 PCIe DMA 取命令和数据。这里是字节带宽的第一道硬墙，也是唯一一处"大 I/O 比小 I/O 更容易撞到"的地方。

除了带宽本身，还有 TLP 头部开销、MPS（Max Payload Size）、以及 DMA 描述符管理成本。小 I/O 在这里浪费的是有效载荷比例，大 I/O 消耗的是纯带宽。

**能拧的旋钮**：确认链路真的跑在标称的代数和宽度上（x4 Gen4 被协商成 x2 或 Gen3 是常见事故）；NUMA 亲和，别让数据跨 socket 搬；IOMMU 开着的开销来自每次 DMA mapping 都要建立和拆除 IOVA 映射（[细节](/hardware/aio-path#pin-page-iova)），高 IOPS 下评估是否需要 passthrough。

## 6. 控制器与 FTL：命令处理率 {#controller}

SSD 控制器需要处理 NVMe 命令解析、FTL 地址映射、请求调度、ECC/LDPC、垃圾回收、wear leveling、加密、RAID-like NAND 保护、DMA 和 PCIe 管理。

如果控制器每秒只能完成 100 万次命令处理，即使 NAND 阵列有能力完成 150 万 IOPS，整盘也只能做到约 100 万 IOPS。

内部 DRAM/SRAM 影响 FTL 映射命中率、写缓冲、元数据访问、GC 搬迁、请求队列管理。如果映射不在 DRAM 缓存中，控制器可能需要先从 NAND 读取映射页，再读取真正数据。这类额外访问会放大延迟，降低 IOPS。

**能拧的旋钮**：这一站主机侧几乎拧不动，只能选型时看清楚 —— 有没有独立 DRAM（DRAM-less 盘靠 HMB 借主机内存，随机性能塌得很快）、映射粒度多大、标称 IOPS 是在什么盘况下测的。主机侧唯一能做的是缩小工作集，让热点的映射页留在控制器缓存里。

## 7. NAND：并行度的来源 {#nand-parallel}

NAND 本身并不快，尤其是写入和擦除：

```text
读：几十到数百微秒
编程：数百微秒到数毫秒
擦除：数毫秒
```

具体值随 SLC、TLC、QLC、代际和工作状态变化。单个 die 在执行内部操作时无法同时处理其他请求，这就产生单 die 服务率上限。

数据从 cell 到主机内存中间还有几道中转：`NAND page buffer → 控制器/ECC → SSD SRAM 或 DRAM → PCIe DMA → 主机 DRAM`。所谓 DMA "直接"，指的是不需要 CPU 逐字节搬运，不是物理路径上没有缓冲（[细节](/hardware/aio-path#read-path)）。

高 IOPS 的关键不是让单次 NAND 操作快到纳秒级，而是靠并行。假设控制器可以让 64 个 die 并行工作，一次读 100 μs：

```text
64 / 100 μs = 640K IOPS
```

但并行度不是简单乘法，层级结构决定了它的含义：

```text
SSD
 ├── Channel          独立数据通路，真正并行，最重要的并行来源
 │    ├── Package
 │    │    ├── Die    共享 channel 总线，但可交错工作
 │    │    │    ├── Plane   受地址对齐限制的 multi-plane 操作
 │    │    │    └── Plane
```

同一 channel 下多个 die 共享传输总线，但可以交错：

```text
Die A：内部读取
Die B：通过 channel 传输
Die C：内部编程
```

所以增加 die 可以隐藏 NAND 内部延迟，增加 channel 才能提升实际并行数据传输能力；同一个 channel 下无限增加 die，不会带来线性增长。不能简单地说有 128 个 die 就有 128 路独立并行，实际并行度受 channel 数、die 组织方式、请求地址分布、flash 命令限制和固件调度能力共同约束。

**能拧的旋钮**：让请求地址分散，别让访问集中砸在少数 die 上（顺序大文件反而容易做到，因为 FTL 通常把连续 LBA 条带化铺到所有 channel）；I/O 大小和对齐匹配内部页大小，避免一次主机读触发多个 NAND page read；保持足够 QD 让所有 die 有活干。

## 8. 完成路径：CQE 与 MSI-X {#completion-cpu}

SSD 写入 CQE，触发 MSI-X 中断。如果所有 completion 都落在同一个 CPU，该 CPU 处理中断和 softirq 的能力会到达上限，其他 CPU 仍然空闲，整体 IOPS 封顶。

**能拧的旋钮**：MSI-X 向量数要够，IRQ affinity 摊开；让提交 CPU 和完成 CPU 尽量是同一个（缓存亲和）；低延迟场景用轮询（`io_uring` 的 `IOPOLL`）代替中断，用 CPU 换延迟；高 IOPS 场景反过来靠中断合并省 CPU。

## 9. 小结：整条链路取最小 {#iops-min}

把各层看作独立处理站，整体上限近似是各站上限的最小值：

```text
IOPS_max = min(
    应用提交能力,
    CPU / 软件栈,
    block layer,
    NVMe 队列,
    PCIe 命令与数据,
    SSD 控制器,
    NAND 阵列
)
```

举个假想例子：

| 环节 | 最大处理能力 |
|---|---:|
| 应用提交 | 2.0M IOPS |
| 内核与驱动 | 1.4M IOPS |
| PCIe 数据带宽折算 | 1.8M IOPS |
| SSD 控制器 | 1.2M IOPS |
| NAND 阵列 | 0.9M IOPS |

最终只能得到约 0.9M IOPS。

这个 min 结构对"怎么压榨"有一个直接推论：**优化非瓶颈环节没有任何收益**。上面这块盘，你把提交路径从 2.0M 优化到 4.0M，对外能力一点不变。所以压榨的第一步永远是定位瓶颈站，而不是照着优化清单挨个试。第三部分讲怎么定位。

另外瓶颈会随 workload 迁移：如果换成更大的 I/O，PCIe 数据带宽折算出的 IOPS 会快速下降，瓶颈就从 NAND 随机访问能力转移到 PCIe 带宽。

# 第二部分 · 三条横切规律

上面是按空间切的。还有三条规律横跨所有站点，它们决定了同一块盘在不同用法下能压榨出多少。

## 10. 队列深度：为什么先涨后平 {#queue-depth}

设平均完成延迟为 L，在途请求数为 QD，根据 Little's Law：

```text
IOPS ≈ QD / L
```

平均延迟 100 μs 时：

| QD | 理想 IOPS |
|---:|---:|
| 1 | 10K |
| 4 | 40K |
| 32 | 320K |
| 64 | 640K |

QD=1 时，主机是"提交 → 等 100 μs → 完成 → 再提交"，SSD 内部可能只有一个 die 在工作，其他 channel/die 全闲着。增加 QD 后控制器手里有更多请求，可以分发到不同 channel、在一个 die 等待时用另一个 die、聚合 PCIe 传输、隐藏 NAND 延迟、提高中断合并效率。

但到某个点后内部资源满载 —— 所有 channel 繁忙、所有可用 die 繁忙、控制器处理器满载、PCIe 或内部总线满载。继续增加 QD 不再提高完成速率，只是让请求排队：

```text
Latency ≈ QD / IOPS_max
```

设备上限 1M IOPS 时，QD=100 平均延迟约 100 μs，QD=1000 就趋向 1 ms。饱和后最典型的现象是：

> 吞吐量不再增长，但平均延迟和尾延迟继续上升。

**压榨含义**：QD 是免费的性能，但只在饱和点之前。找到那个拐点，是调优的第一件事 —— 低于它是浪费硬件，高于它是白白抬高延迟。

## 11. 小 I/O 与大 I/O：两种不同的天花板 {#io-size}

4 KiB 随机读和 1 MiB 顺序读都要经历一次相近的固定流程：

```text
解析命令 → FTL 查找 → 调度 NAND → DMA → 写 CQE → 通知 CPU
```

4 KiB 请求的数据很少，但固定开销没少多少，所以它受"每秒能处理多少条命令"限制。1M IOPS 的盘做 4 KiB 是约 4 GiB/s；换成 1 MiB I/O，即使只做 7,000 IOPS 也有约 7 GiB/s，此时先撞到的是 PCIe、NAND channel 或内部数据通路的带宽上限。

> 小 I/O 通常受命令处理率和访问延迟限制；大 I/O 通常受字节带宽限制。

基本关系是 `Bandwidth = IOPS × IOSize`。厂商数据中的"最大 IOPS"和"最大带宽"通常不能同时达到，因为它们来自不同 workload。

顺便回答一个常见疑问：SSD 没有机械寻道，随机读为什么不能无限快？因为"无寻道"只消除了机械臂和旋转等待，没有消除 NAND page read 延迟、FTL 映射、ECC 解码、channel 占用、PCIe 事务、命令解析、DMA 描述符管理、完成队列处理。而且一个 4 KiB 主机读，内部可能对应一次更大粒度的 NAND page read、一次映射页读取、多轮 LDPC 解码甚至 read retry。

顺序访问的优势也不在"少了寻道"，而在于让控制器更容易预取、更容易识别连续范围、降低映射访问开销、提高 channel 传输效率、减少命令固定成本占比。

**压榨含义**：合并小 I/O 是最直接的手段 —— 它同时省掉命令处理成本和内核软件栈成本。但合并到多大有上限：除了超过内部条带宽度后收益消失，还有一道硬限制是 PRP 能描述的内存段数有限，超了就必须把一个用户 I/O 拆成多条 NVMe command（[细节](/hardware/aio-path#prp-sgl)）。顺带一提，`O_DIRECT` 那些对齐要求也源于此 —— PRP list 里的每一项都必须页对齐，缓冲区不对齐就没法描述。

## 12. 写路径：无效工作从哪来 {#write-path}

写比读多做很多事：

```text
主机数据 → SSD 缓冲区 → 分配新物理页 → NAND program
        → 更新 FTL 映射 → 旧页失效 → 未来 GC 迁移 → 擦除 block
```

因为 NAND 不能原地覆盖，覆盖写最终会制造垃圾。盘比较空时空闲块多、SLC cache 充足，写入看起来很快；长时间写入后 SLC cache 耗尽、空闲块减少、GC 启动、有效 page 需要搬迁、映射和元数据需要更新。于是 host write 和内部 GC 开始争抢 NAND channel、die、控制器算力、DRAM 带宽和空闲块。

假设主机每写 1 单位数据，SSD 实际写 3 单位，即写放大 WA=3。如果 NAND 最多能承受 6 GB/s 写入，主机可见写带宽理论上只剩 2 GB/s。

这是第三条优化路径（消除无效工作）最典型的战场，也是主机侧最有作为的地方。**能拧的旋钮**：增大 over-provisioning（少用一部分容量换稳态性能）；顺序写和按 block 对齐覆盖，让整块失效而不是零散失效；及时 TRIM/discard 告诉盘哪些块不用搬；把冷热数据分开写，避免 GC 反复搬运冷数据。

评估写性能必须看稳态而不只是刚开始几十秒，同时看盘的填充程度、over-provisioning、随机还是顺序、数据可压缩性、是否触发 GC、写缓存是否耗尽。

还有一件事必须先问清楚，否则测出来的写延迟不知道代表什么：**写命令完成不等于数据落到 NAND**。它可能只表示数据进了控制器的易失性写缓存（VWC）。真正的持久化取决于盘有没有断电保护（PLP）、命令是否带 FUA、主机是否发了 Flush、文件系统何时提交元数据和日志（[细节](/hardware/aio-path#write-durability)）。所以同一块盘，带不带 `fsync` 测出来可以差一个数量级，而这个差值不是性能问题，是语义问题 —— 对比前先确认两边处在同一个持久化域上。

## 13. 尾延迟：平均值掩盖的东西 {#tail-latency}

平均延迟低不代表每个请求都快。少数请求可能碰到 FTL mapping cache miss、多轮 ECC/LDPC 解码、read retry、GC 搬迁、block 擦除、wear leveling、thermal throttling、固件后台任务、队列头阻塞、PCIe 错误恢复、文件系统元数据锁、CPU 调度延迟。

例如绝大多数读是 80 μs，但某个老化的 QLC page 需要多轮 read retry，就可能达到毫秒级。

尾延迟本质上是前面每一站异常态的叠加，所以它是判断"这块盘还剩多少余量"最灵敏的指标 —— 平均 IOPS 封顶之前，P99 往往已经开始恶化。评估时看 P50、P95、P99、P99.9、最大延迟，以及不同 QD 下的延迟分布。

# 第三部分 · 定位与总结

## 14. 从测试形状反推瓶颈 {#diagnose}

第 9 节说过，优化非瓶颈环节没有收益，所以定位优先于调优。下面这张表是从 fio 曲线形状反推瓶颈站的对照：

| 观察到的现象 | 瓶颈判断 | 下一步 |
|---|---|---|
| QD 增加，IOPS 线性增加 | 设备未饱和，只是并行度不足 | 继续加 QD 或加线程 |
| QD 增加，IOPS 不变、延迟上升 | 某个资源已饱和，新请求在排队 | 定位是哪一站，别再加 QD |
| 增加 I/O 大小，带宽涨但 IOPS 降 | 正从命令率限制转向带宽限制 | 检查 PCIe 链路和内部通路 |
| 多线程后 IOPS 明显增加 | 原来受单 CPU、单队列或提交并行度限制 | 继续摊开提交路径 |
| 多线程后 IOPS 不变 | 已受控制器/NAND/PCIe 限制，或线程在抢同一共享资源 | 先区分是设备满了还是软件在争 |
| 短时间写很快，持续写后骤降 | SLC cache 耗尽、GC、写放大进入稳态 | 调 OP、改写模式、加 TRIM |
| 读性能随盘老化下降、尾延迟增加 | retention、ECC 解码次数、read retry、后台刷新 | 盘本身的问题，主机侧无解 |
| CPU 100% 但设备利用率不高 | 主机软件栈、buffer copy、锁竞争、页管理、中断处理 | 回到第 1~4 节的旋钮 |

## 15. 一句话总结

> SSD 的 IOPS 上限，本质上是有限并行资源和非零服务时间共同产生的。单个 NAND die 执行一次读、编程或擦除都需要时间，SSD 通过多个 channel 和 die 并行来提高 IOPS；但 channel 带宽、die 数量、控制器算力、FTL、ECC、内部 DRAM 以及 PCIe 都是有限的，所以并行度到达饱和点后，继续增加队列深度只会增加排队延迟，不再提高 IOPS。
>
> 对小随机 I/O，瓶颈通常体现为每秒命令处理能力和 NAND 并行度；对大 I/O，通常更容易撞到 PCIe 或 NAND channel 带宽；对持续随机写，还会受到 out-of-place update、GC 和写放大的影响。整体性能最终由主机 CPU、内核、PCIe、SSD 控制器和 NAND 阵列中最慢的环节决定。

最关键的一句：

> **IOPS 不是一个凭空存在的产品参数，而是"并行资源数量 ÷ 每次占用资源的时间"，再受到软件、控制器和总线瓶颈约束后的结果。**

而"压榨"这块盘，就是沿着这条链路做三件事：把闲着的并行资源用起来，把每次占用的时间缩短，把不产生对外能力的无效工作消掉 —— 并且只对当前的瓶颈站做。
